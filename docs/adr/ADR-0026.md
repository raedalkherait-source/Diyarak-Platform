# ADR-0026: Create authenticated Market Listing drafts for existing Properties

**Status:** Accepted

## Decision

`Diyarak.Api` will expose `POST /api/market/listings` for creating a new Market Listing draft when authentication is enabled.

The operation requires the same mapped internal user authorization policy defined by ADR-0025. The defined request contract contains only the referenced Property identifier. `PublisherUserId` is not a request field, and client-supplied data must not influence the publisher identity.

After authentication and external-identity resolution succeed, the Host supplies the mapped internal `User.Id` to Application orchestration. That identifier becomes the new Listing's immutable `PublisherUserId`.

The initial request contract is:

```json
{
  "propertyId": "00000000-0000-0000-0000-000000000001"
}
```

The initial creation workflow is intentionally limited to the already-supported `market.property` subject type. `CreateListingUseCase` validates the Property and actor identifiers, verifies that the referenced Property exists through `IPropertyExistenceChecker`, creates a new Listing with a generated non-empty identifier and `Draft` status, and persists it through `IMarketListingRepository`.

`IMarketListingRepository` therefore distinguishes adding a new Listing from saving a previously loaded Listing. `AddAsync` is the persistence operation for creation; `SaveAsync` remains the persistence operation for an existing aggregate.

The HTTP response contract is:

- `201 Created` when the Draft Listing is created and persisted. The response body contains the generated `listingId`, and `Location` identifies `/api/market/listings/{listingId}`.
- `400 Bad Request` when `propertyId` is missing, malformed, or empty.
- `401 Unauthorized` when the bearer access token is missing or invalid.
- `403 Forbidden` when the access token is valid but its exact `(iss, sub)` identity has no internal user mapping.
- `409 Conflict` when the referenced Property does not exist at creation time.
- `500 Internal Server Error` for unexpected persistence or programming failures.

Expected Application failures use stable error codes:

- `market.listing.invalid_property_id`
- `market.listing.invalid_actor_id`
- `market.listing.property_not_found`

Creation does not set `ListingContext`, `ListingHeadline`, `ListingPrice`, or `ListingAvailableFromDate`. Those values remain optional while the Listing is `Draft` and the existing publication rules continue to require context, headline, and price before publication.

The Property existence check and Listing insert currently share the same scoped persistence integration but are not protected by a newly introduced explicit transaction, lock, or isolation guarantee. Optimistic concurrency, Property lifecycle behavior, draft editing endpoints, deletion, ownership transfer, administrative overrides, and creation for additional subject types remain separate decisions.
