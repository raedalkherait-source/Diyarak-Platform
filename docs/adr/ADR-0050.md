# ADR-0050: Per-client rate limiting and public result window

## Status

Accepted

## Context

The Host registered a single fixed-window limiter (100 requests per minute) that was shared by
every caller and applied only to `GET /`. The anonymous public Listing routes
(`/api/market/public/listings` and `/api/market/public/listings/{listingId}`) were not limited at
all, and if the shared limiter had been applied to them, one client could exhaust the window for
every other client.

The public collection also accepted any `page` whose offset fit in `int`, allowing anonymous
clients to request arbitrarily deep `OFFSET` scans. The root endpoint disclosed the hosting
environment name.

## Decision

- Replace the named shared limiter with a global limiter partitioned by client IP address
  (`HttpContext.Connection.RemoteIpAddress`). Each client gets its own fixed window, configured
  through `RateLimiting:PermitLimit` (default `100`) and `RateLimiting:WindowSeconds`
  (default `60`). Invalid values fail at startup.
- The limiter applies to every route, including public and authenticated Market routes. `/health`
  probes are exempt so orchestrators are never throttled.
- Rejected requests return `429 Too Many Requests` with a `Retry-After` header.
- `ListPublishedListingsUseCase.MaximumResultWindow` is `10,000` rows. Pages whose offset reaches
  the window are rejected with the existing `market.public_listings.invalid_pagination` error, and
  the last addressable page reports `hasMore = false`, so no `next` link points outside the window.
- `GET /` no longer returns the environment name or a hard-coded version.

## Consequences

Anonymous traffic can no longer starve other clients or force unbounded offset scans. Deployments
behind a reverse proxy or CDN must configure forwarded headers for trusted proxies only; until that
is configured, all traffic arriving through the proxy shares the proxy's partition. Clients that
need results beyond the window must narrow their filters.
