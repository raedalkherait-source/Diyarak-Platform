# ADR-0034: Establish authenticated Market Property management ownership

**Status:** Accepted

## Context

ADR-0030 introduced authenticated Property creation, and ADR-0031 added authenticated direct loading by identifier. Those workflows deliberately stopped short of defining Property ownership because the product requirements had not yet established who controls a Property resource inside Diyarak.

That omission now blocks safe Property management evolution. Without a stable management owner, future Property collection, update, archive, or removal workflows cannot distinguish the actor allowed to operate on a Property from another mapped user who merely knows its identifier.

This decision concerns ownership of the Diyarak Property resource for authorization and management. It does not represent or prove legal title to real estate, tenancy rights, brokerage authority, or any other real-world property right.

Existing `market.properties` rows may predate this decision. Diyarak has no authoritative historical mapping that can safely assign those rows to internal users, so the migration must not invent or backfill owners.

## Decision

Every Property created through `POST /api/market/properties` after this decision is assigned the mapped internal actor `User.Id` as its immutable `OwnerUserId`.

`CreatePropertyUseCase` receives the current actor user identifier separately from request data. The actor identifier must be non-empty, is not accepted from the HTTP request body, and is passed by the Host only after the existing ADR-0025 `mapped-user` authorization policy has succeeded.

The Property aggregate records `OwnerUserId` as an optional immutable value so that pre-ADR-0034 legacy rows can still be reconstructed. A present owner identifier must be non-empty. Newly created Properties always receive a non-empty owner.

`GET /api/market/properties/{propertyId}` becomes owner-only management access. `GetPropertyUseCase` receives the mapped actor user identifier, loads the Property, and returns the same `market.property.not_found` result when the Property is missing, belongs to another user, or is a legacy row with no owner. This concealed `404` prevents the direct-management endpoint from revealing whether another user's Property identifier exists.

The HTTP response continues to omit `OwnerUserId`. Ownership is an authorization key, not a client-selectable field or public representation field.

PostgreSQL adds nullable `market.properties.owner_user_id uuid`. The column has no default and no data backfill. A check constraint permits `NULL` for legacy rows but rejects the all-zero GUID when an owner is present. The full-state record and mapper preserve both owned and legacy-unowned states.

No ownership transfer, delegation, company ownership, administrative override, Property update/removal workflow, or owned-Property collection is defined by this decision.

This decision also does not change Listing subject authorization. `CreateListingUseCase` continues to require only that the referenced Property exists. Whether Listing creation must require Property ownership, delegated rights, or another publication authority remains a separate product decision because shared and professional-agent publication semantics are not yet defined.

## Consequences

New Property resources now have a stable internal management owner that can support later owner-scoped Property operations without trusting user identifiers from request payloads.

Direct Property loading is no longer available to every mapped user who knows an identifier. Missing, non-owned, and legacy-unowned Properties share the same concealed `404` management result.

Existing Property rows remain unowned until an authoritative mapping is supplied through a separately reviewed migration or provisioning process. The schema migration is therefore safe for environments containing legacy Property data and does not fabricate ownership.

Public Property presentation, legal ownership semantics, Listing publication authority over a Property, ownership transfer/delegation, administrative access, Property lifecycle, concurrency, update/removal, and collection/search behavior remain separate requirements.
