# ADR-0035: Add the authenticated owned-Property management collection

**Status:** Accepted

## Context

ADR-0034 established immutable internal management ownership for newly created Market Properties and converted direct Property loading to owner-only concealed access. A mapped user can therefore create a Property and load a known owned Property identifier, but there is still no management operation that lets that user retrieve the set of Property resources they own.

The Listing side already has the corresponding owner-scoped management collection through ADR-0033. Property ownership now provides the authorization key needed to add the same narrow capability without defining public Property discovery, search, pagination, ranking, or administrative access.

Legacy `market.properties` rows may still have `owner_user_id = NULL` because ADR-0034 intentionally performed no historical ownership backfill. Those rows must not be exposed through an owner-scoped collection until an authoritative owner is assigned.

## Decision

Add mapped-user-only `GET /api/market/properties` as the current actor's Property management collection.

The Host obtains the non-empty internal actor `User.Id` only from the ADR-0025 authenticated actor accessor and passes it to `ListOwnedPropertiesUseCase`. The request accepts no owner or user identifier.

`ListOwnedPropertiesUseCase` validates the actor identifier and asks the Application-owned `IMarketPropertyRepository` for Properties whose persisted `OwnerUserId` equals that actor.

`IMarketPropertyRepository` adds `FindByOwnerUserIdAsync`. The PostgreSQL implementation performs a no-tracking query filtered by `owner_user_id` and maps only matching records back to the Property aggregate. Rows owned by another user and legacy rows whose owner is `NULL` are excluded by the query.

Successful collection reads return `200 OK` with a JSON array using the same authenticated management representation as owner-only direct Property loading. The response omits `OwnerUserId`; ownership remains an authorization key rather than a client-facing selectable field.

Missing or invalid access tokens continue to return `401`, and valid but unmapped external identities continue to return `403`, through the existing ADR-0025 policy. When authentication is disabled, the route is not mapped.

An owner with no matching Properties receives `200 OK` with an empty array.

This decision defines no result ordering. It also defines no pagination, filtering, search, public Property discovery, administrative collection, ownership transfer/delegation, Property update/removal workflow, or lifecycle behavior.

## Consequences

Mapped users can now manage the discovery of their own Property resources without knowing identifiers in advance and without exposing other users' or legacy-unowned Property rows.

The query remains narrow and ownership-scoped, so it does not create a public Property browsing contract or require new indexes, schema migrations, ordering metadata, or pagination semantics at this stage.

Future pagination or ordering requirements may change the collection contract and may require persisted ordering fields or indexes. Those decisions remain deferred until concrete requirements exist.
