# ADR-0027: Execute Market Listing creation and publication inside explicit PostgreSQL transactions

**Status:** Accepted

## Decision

The existing Market Listing creation and publication workflows will execute their persistence-sensitive work inside one explicit transaction owned by an Application port.

`Diyarak.Market.Application` introduces `IMarketTransactionRunner`. `CreateListingUseCase` and `PublishListingUseCase` validate their required identifiers before entering the transaction, then execute the persistence-sensitive workflow through that port.

For Listing creation, the transaction contains:

1. the referenced Property existence query;
2. construction of the new actor-owned `Draft` Listing; and
3. `IMarketListingRepository.AddAsync`.

For Listing publication, the transaction contains:

1. Listing loading;
2. creator-ownership validation;
3. the referenced Property existence query;
4. the `Listing.Publish()` transition; and
5. `IMarketListingRepository.SaveAsync`.

`Diyarak.Platform.Persistence.PostgreSql` implements the port as `PostgreSqlMarketTransactionRunner` using the same scoped `PlatformDbContext` as the Property checker and Listing repository. The transaction uses PostgreSQL `ReadCommitted` isolation.

Because PostgreSQL retry-on-failure is already enabled for the DbContext, the explicit transaction is executed through EF Core's configured execution strategy rather than starting an unsupported user transaction outside that strategy.

A successful Application `Result` commits the transaction. An expected failed `Result` rolls it back. Unexpected exceptions also trigger rollback and continue to the existing Host exception boundary.

This decision does not introduce a new database migration.

## Boundaries

This transaction boundary provides atomic commit/rollback for the currently defined Listing operation and its persistence work. It does not claim a stronger cross-aggregate referential-integrity guarantee than PostgreSQL `ReadCommitted` provides.

In particular, this decision does **not** introduce:

- an explicit row lock on the referenced Property;
- `RepeatableRead` or `Serializable` isolation;
- optimistic concurrency for competing Listing writes;
- a Property deletion or archival rule;
- a rule preventing a Property from becoming unavailable after a successful Listing operation; or
- a distributed transaction outside the current PostgreSQL persistence boundary.

Those behaviors remain separate decisions because the project does not yet define Property mutation/removal workflows or the required conflict semantics for competing Listing operations.

## Consequences

The Property existence query and Listing insert/save no longer rely on separate implicit persistence commits. The transaction boundary is explicit, test-substitutable at the Application layer, and implemented by the PostgreSQL integration without leaking EF Core transaction APIs into the domain or Host.

Application validation failures for empty identifiers occur before opening a transaction. Expected failures discovered inside the workflow, such as a missing Property or a concealed missing/non-owned Listing, roll back the transaction without persisting state.
