# ADR-0046: Explicit public Listing revalidation cache policy

## Status

Accepted and implemented.

## Context

ADR-0044 and ADR-0045 add strong opaque ETags and `If-None-Match` revalidation to anonymous published-Listing detail and collection responses. Those ADRs intentionally stop short of defining a `Cache-Control` policy, leaving intermediaries and clients without an explicit instruction about whether successful public responses may be stored and whether they must be revalidated before reuse.

The public Listing representations are anonymous and intentionally contain only publication-facing fields. They can therefore be stored by shared caches, but the current product model has no positive freshness lifetime and no guarantee that a published representation remains unchanged for any fixed period. Negative responses are also not stable: a missing identifier may later become visible, and an invalid pagination request should not be retained as a reusable representation.

## Decision

Successful anonymous public Listing responses from both:

- `GET /api/market/public/listings/{listingId}`; and
- `GET /api/market/public/listings`

use:

```text
Cache-Control: public, no-cache
```

The same directive is present on `304 Not Modified` responses produced by matching `If-None-Match` validators.

`public` permits storage by shared as well as private caches. `no-cache` requires successful reuse to be validated with the origin server rather than assigning a positive freshness lifetime. The existing opaque ETag validators from ADR-0044 and ADR-0045 provide that revalidation mechanism.

Expected public error responses produced by these routes, currently `400 Bad Request` and concealed `404 Not Found`, use:

```text
Cache-Control: no-store
```

This prevents retention of negative or invalid-request responses that may not remain meaningful for later requests.

The policy is applied at the public Market Host boundary. It does not change response bodies, status codes, ETag construction, pagination, publication visibility, or the ADR-0043 authenticated management `no-store` policy.

This ADR does not define a positive `max-age`, `s-maxage`, `stale-while-revalidate`, CDN-specific directive, Last-Modified timestamp, immutable response guarantee, search/filter/ranking semantics, or public Property representation.

## Consequences

Clients and shared caches may store successful anonymous public Listing representations, but must revalidate before reuse. Unchanged representations can therefore reuse the existing ETag flow and receive `304 Not Modified` without transferring the JSON body.

Public expected errors are never intentionally cached by this Host policy. Management responses remain separately governed by ADR-0043 and continue to use `Cache-Control: no-store`.
