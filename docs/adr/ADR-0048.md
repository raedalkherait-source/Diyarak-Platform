# ADR-0048: Public Listing collection pagination Link headers

## Status

Accepted

## Context

ADR-0039 defines bounded anonymous pagination for the published Listing collection using `page`, `pageSize`, and `hasMore`. ADR-0045 through ADR-0047 add page-specific ETag revalidation, explicit cache policy, and GET/HEAD parity. Clients can determine whether another page exists from the JSON `hasMore` field, but HTTP clients and HEAD callers currently receive no standard navigation metadata.

Adding navigation links is transport metadata and does not require search, ranking, total-count, or lifecycle decisions.

## Decision

Successful responses from the anonymous public Listing collection expose HTTP `Link` header navigation derived only from the already-defined page coordinates and `hasMore` value:

- when `page > 1`, include `</api/market/public/listings?page={page-1}&pageSize={pageSize}>; rel="prev"`;
- when `hasMore` is `true` and `page` is below the maximum accepted 32-bit page value, include `</api/market/public/listings?page={page+1}&pageSize={pageSize}>; rel="next"`;
- when both apply, emit `prev` first and `next` second in the same `Link` header;
- when neither applies, omit the `Link` header.

The links preserve the effective `pageSize` used for the current request. They intentionally use the existing public collection path and do not add or preserve undefined filter, search, ranking, or sorting parameters.

The same navigation metadata is emitted for `GET`, `HEAD`, and `304 Not Modified` responses for the page. Expected `400` pagination errors do not carry page-navigation links.

ADR-0045 ETag generation is unchanged. Navigation links are fully derivable from page coordinates and `hasMore`, which are already part of the page validator input.

No `rel="last"` link is defined because the collection intentionally has no `totalCount` contract. No `rel="first"` link is required by this ADR. If the current page is already `Int32.MaxValue`, no unrequestable overflowed `next` link is emitted even if the bounded query reports `hasMore`.

## Consequences

- Clients can navigate forward and backward without parsing the JSON body, including when using `HEAD`.
- Conditional `304` responses retain enough metadata to navigate relative to the validated page.
- `next` continues to mean only that the bounded query observed another row through the existing `hasMore` mechanism; it does not introduce a total-count or snapshot guarantee.
- Public projection, ordering, pagination bounds, ETag values, cache policy, authorization, and persistence remain unchanged.
- No schema or migration change is required.
