# ADR-0041: Market management ownership query indexes

## Status

Accepted and implemented.

## Context

ADR-0033 introduced authenticated management collection loading for Listings owned by the current publisher through `GET /api/market/listings`. The PostgreSQL repository filters `market.listings` by persisted `publisher_user_id`.

ADR-0035 introduced authenticated management collection loading for Properties owned by the current management owner through `GET /api/market/properties`. The PostgreSQL repository filters `market.properties` by persisted `owner_user_id`; legacy rows whose owner is `NULL` are excluded by that equality predicate.

Neither ownership column currently has a dedicated database index. As each table grows, those confirmed owner-scoped management access patterns should have persistence indexes without changing the management API or inventing pagination or ordering semantics that are still undefined.

## Decision

`MarketListingRecord` defines a non-unique index on `PublisherUserId` named:

`ix_market_listings_publisher_user_id`

`MarketPropertyRecord` defines a non-unique index on nullable `OwnerUserId` named:

`ix_market_properties_owner_user_id`

The `MarketManagementOwnershipQueryIndexes` migration creates the corresponding B-tree indexes on:

- `market.listings(publisher_user_id)`;
- `market.properties(owner_user_id)`.

The migration removes both indexes on rollback.

The indexes exist only to support the confirmed equality filters already used by the authenticated management collections. They do not define or imply result ordering, pagination, public discovery, delegated ownership, or ownership-transfer semantics.

No Domain, Application, Host, response-shape, authentication, authorization, or lifecycle changes are introduced.

## Consequences

The two existing owner-scoped management collection queries now have persistence indexes aligned with their confirmed predicates.

Legacy Property rows with `owner_user_id = NULL` remain unowned and remain excluded from the authenticated owner collection. This ADR does not assign ownership to those rows.

Future pagination or ordering requirements may require different or additional composite indexes and must be designed from the confirmed query contract rather than inferred from these indexes.

A database migration is required.
