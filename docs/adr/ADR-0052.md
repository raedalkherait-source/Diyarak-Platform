# ADR-0052: Phone-number sign-in with platform-issued access tokens

## Status

Accepted

## Context

ADR-0025 made the API validate access tokens from an external OIDC provider and resolve
`(iss, sub)` to an internal user through persisted mappings, but no provider was selected and
there was no way for a user to register. In the Syrian market, users expect to sign in with
their phone number and a one-time code; email-first sign-up and foreign identity providers are
a poor fit.

## Decision

The platform verifies phone numbers itself and issues its own short-lived access tokens, while
keeping the ADR-0025 authorization pipeline unchanged.

Domain (`Diyarak.Platform.Identity`):

- `PhoneVerificationChallenge` stores only a hash of a 6-digit code, expires after 5 minutes,
  is consumed on first successful use, and locks after 5 failed attempts.
- `PhoneAccount` links one E.164 phone number to exactly one internal user.

Application (`Diyarak.Platform.Identity.Application`, new):

- `RequestPhoneVerificationUseCase` validates E.164, allows at most 3 codes per phone number per
  15 minutes, persists the challenge, then sends the code through `IOtpSender`. The response
  never reveals whether the number is already registered.
- `VerifyPhoneUseCase` checks the code against the latest challenge only (constant-time hash
  comparison bound to the challenge id), creates the account on first sign-in, and issues an
  access token through `IAccessTokenIssuer`.
- On first sign-in the account is stored together with an external identity mapping
  `(platform issuer, user id)` in one commit, so platform tokens resolve through the existing
  `IExternalIdentityResolver` and `mapped-user` policy with no special cases.

Persistence:

- Tables `identity.phone_verification_challenges` and `identity.phone_accounts`
  (migration `IdentityPhoneAuthentication`). `failed_attempts` and `consumed_at` are concurrency
  tokens compared against the values observed at load time, so two concurrent verifications
  cannot both consume a code. A duplicate phone account (unique violation) is reported as a
  retryable conflict.

HTTP (`Diyarak.Api`):

- `POST /api/auth/phone/request` `{ phoneNumber }` → `202 { expiresAt }`; `400` invalid number;
  `429` per-phone throttle.
- `POST /api/auth/phone/verify` `{ phoneNumber, code }` →
  `200 { accessToken, tokenType, expiresAt, userId, isNewUser }`; `400` for any invalid,
  expired, reused or locked code (one indistinguishable error).
- Both routes are anonymous, `Cache-Control: no-store`, and use an extra per-IP rate-limit
  policy (`RateLimiting:Otp`, default 10 requests per 15 minutes) on top of ADR-0050.
- Tokens are HS256 JWTs, `typ: at+jwt`, with `iss`, `aud`, `sub` (internal user id, never the
  phone number), `jti`, and a lifetime of `Authentication:Phone:AccessTokenLifetimeMinutes`
  (default 60). There are no refresh tokens yet.
- When external OIDC is also enabled, a policy scheme forwards each bearer token by its
  unvalidated `iss` to either the platform scheme or the OIDC scheme; the selected scheme
  performs full validation, so a token claiming the platform issuer but signed with another key
  is rejected.
- Management routes are mapped when either OIDC or phone sign-in is enabled.

Configuration (`Authentication:Phone`): `Enabled`, `Issuer` (absolute URI), `Audience`,
`SigningKey` (base64, ≥ 32 bytes, from secrets only), `AccessTokenLifetimeMinutes` (5–1440),
`OtpSender`. The only sender today is `DevelopmentLog`, which writes codes to the log; startup
fails if it is configured outside Development or if any setting is invalid.

## Consequences

Users can register and sign in with a phone number without any third-party identity provider,
and all existing authorization, ownership and concealment rules apply to them unchanged.

Before production use:

- an SMS or WhatsApp `IOtpSender` adapter must be implemented as an Integration and selected
  through `Authentication:Phone:OtpSender`;
- the signing key must be provisioned through a secret store and rotated by redeploying;
- refresh tokens or sliding sessions, sign-out/revocation, and cleanup of expired challenges
  remain open work.

ADR-0052 approves the Application → Core dependency
`Diyarak.Platform.Identity.Application` → `Diyarak.Platform.Identity`.
