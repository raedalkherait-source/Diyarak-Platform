# ADR-0038: Public published Listing direct loading

## Status

Accepted and implemented.

## Context

ADR-0032 introduced creator-only direct Listing loading through `GET /api/market/listings/{listingId}`. That endpoint is an authenticated management representation: it exposes the current Listing version, lifecycle status, and immutable subject reference to the mapped creator while concealing non-owned resources.

Diyarak Market scope also includes public APIs, but public Listing detail remained undefined. Reusing the management endpoint anonymously would expose management metadata and blur authorization semantics. Public Property presentation and public subject resolution are still undefined, so a public Listing response must not invent or leak a Property-detail contract.

## Decision

Diyarak exposes a separate anonymous public endpoint:

`GET /api/market/public/listings/{listingId}`

The route is mapped independently of `Authentication:Enabled` and explicitly allows anonymous access. Authenticated management routes remain conditional on OIDC configuration and continue to use the ADR-0025 mapped-user policy.

The Application-owned `GetPublishedListingUseCase` loads the Listing by identifier through the existing `IMarketListingRepository`. It returns a Listing only when its persisted lifecycle state is `Published`.

A missing Listing and a `Draft` Listing return the same `404 Not Found` result using the existing `market.listing.not_found` error. Invalid or empty identifiers return the existing `400 Bad Request` Listing-identifier validation error. No actor identifier or ownership check is part of the public read.

The public response contains only publication-facing Listing data already required or allowed by the current domain model:

- `listingId`
- `context.publishingRole`
- `context.transactionIntent`
- `headline`
- `price`
- optional `availableFromDate`

The response does not expose `PublisherUserId`, Listing `Version`, lifecycle `Status`, `subjectId`, or `subjectType`. The subject reference remains an internal management concern until a separate public Property/subject projection is defined.

This ADR does not define public Listing collections, search, pagination, filtering, ranking, Property presentation, contact workflows, favorites, view counters, caching semantics, or published-Listing editing.

No persistence schema change is required.

## Consequences

Published Listings can now be loaded anonymously by known Listing identifier without requiring an identity-provider configuration. Draft Listings remain non-public and indistinguishable from missing Listings through this endpoint.

Management and public representations are intentionally separate. Future public search or Property-detail work can compose a public subject projection without changing the existing owner-management contract.

Because the public endpoint uses the existing direct repository read, this decision introduces no new persistence port, migration, transaction, or concurrency rule.
