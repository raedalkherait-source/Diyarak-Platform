# ADR-0045: Conditional public Listing collection revalidation with opaque page ETags

## Status

Accepted and implemented.

## Context

ADR-0039 exposes anonymous bounded `Published` Listing collection loading through `GET /api/market/public/listings` with deterministic identifier ordering, `page`/`pageSize`, `hasMore`, and the reduced public projection established by ADR-0038. ADR-0044 adds strong opaque ETag revalidation to direct public Listing detail, but intentionally leaves the collection without a validator because collection membership and pagination require separate invalidation semantics.

The public collection query already returns persisted Listing aggregates with positive numeric versions. A page validator can therefore represent both the requested page coordinates and the current persisted revisions of the Listings that make up that page without exposing those versions in JSON.

## Decision

Successful `GET /api/market/public/listings` responses include a strong opaque `ETag` header.

The validator is derived from:

- a Host-owned public collection representation revision;
- the resolved `page` value;
- the resolved `pageSize` value;
- the page `hasMore` value; and
- the ordered sequence of each returned Listing identifier and persisted Listing version.

The derivation is hashed with SHA-256 before being emitted. The public header therefore does not expose Listing identifiers or numeric versions in clear text. Including page coordinates prevents a validator for one requested page shape from being reused for another, and including `hasMore` captures a change at the page boundary even when the visible items remain otherwise unchanged.

When the request contains `If-None-Match` and one of its validators weakly matches the current page validator, or the header contains `*`, the endpoint returns `304 Not Modified`, includes the current `ETag`, and returns no representation body. A non-matching or absent `If-None-Match` returns the existing `200 OK` page representation plus the current `ETag`.

Pagination validation and the published-only query still occur before conditional evaluation. Invalid pagination therefore retains `400 Bad Request`, and the Application's fail-closed `Published` invariant remains unchanged.

This ADR does not define a positive cache freshness lifetime, CDN policy, `Cache-Control` directive for public responses, Last-Modified timestamps, total-count semantics, search/filter/ranking behavior, or a cursor-pagination contract.

No persistence, Domain, or Application schema/contract change is required.

## Consequences

Clients can cheaply revalidate an unchanged public collection page and receive `304 Not Modified` instead of the page JSON.

A change to any visible Listing version, page membership/order, page coordinates, or `hasMore` changes the validator. The internal Listing versions remain absent from public JSON and are not directly observable from the opaque hash.

Collection ETags remain page-specific technical validators and do not establish business ranking, freshness guarantees, or immutable pagination snapshots across concurrent writes.
