# ADR-0025: Authenticate API callers through external OIDC identities

**Status:** Accepted

## Decision

`Diyarak.Api` will act as an OAuth 2.0 resource server and accept bearer access tokens issued by an explicitly configured trusted OpenID Connect identity provider.

Diyarak will not issue access tokens or manage passwords as part of this decision.

The API must validate each access token's signature, issuer, audience, and lifetime before accepting its principal. ID tokens must not be accepted as API access tokens. Trusted issuers and audiences are explicit configuration; wildcard trust is not permitted.

An authenticated external identity is identified only by the exact non-empty `iss` and `sub` claims. These values remain opaque. Email address, display name, and other mutable claims must not be used as identity keys.

A persistent mapping will resolve each unique `(issuer, subject)` pair to one non-empty internal `Diyarak.Platform.Identity.User` identifier.

`Diyarak.Platform.Persistence.PostgreSql` is explicitly approved to reference `Diyarak.Platform.Identity` for the `ExternalIdentity` and `IExternalIdentityResolver` contracts required to implement this persistent mapping.

One internal user may have multiple external identity mappings. Each `(issuer, subject)` pair may map to only one internal user.

External identity mappings must be provisioned explicitly through a separate trusted workflow. Resource operations such as Listing publication must not create users, create mappings, or link accounts automatically. Email-based automatic linking is prohibited.

A missing or invalid access token results in `401 Unauthorized`. A valid access token whose `(issuer, subject)` has no internal mapping results in `403 Forbidden`.

After successful resolution, the Host supplies the internal `User.Id` to Application orchestration as the authenticated actor identifier. An authenticated and mapped non-owner still receives the concealed `404 Not Found` publication outcome defined by ADR-0023.

The publication endpoint remains unmapped until JWT bearer validation, external-identity resolution, failure handling, and configuration are implemented and verified.

Identity-provider vendor selection, user provisioning transport, account linking and unlinking, token acquisition and refresh, administrative overrides, and ownership transfer remain separate decisions.
