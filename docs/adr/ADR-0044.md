# ADR-0044: Conditional public Listing detail revalidation with opaque ETags

## Status

Accepted and implemented.

## Context

ADR-0038 exposes anonymous direct loading of a `Published` Listing through `GET /api/market/public/listings/{listingId}` with a reduced public projection. ADR-0043 deliberately keeps that public route outside the authenticated management `no-store` policy, but no public cache validator has been defined.

The persisted Listing already has a positive numeric version used for optimistic concurrency. Exposing that numeric version directly would conflict with the public projection boundary established by ADR-0038, while ignoring it would miss an existing representation-change signal.

## Decision

Successful `GET /api/market/public/listings/{listingId}` responses include a strong opaque `ETag` header.

The validator is derived from:

- a Host-owned public representation revision;
- the Listing identifier; and
- the persisted Listing version.

The derivation is hashed with SHA-256 before being emitted, so the public header does not expose the internal numeric Listing version or embed the Listing identifier in clear text. The representation revision ensures that a future incompatible public projection change can invalidate validators even when persisted Listing state is unchanged.

When the request contains `If-None-Match` and one of its validators weakly matches the current public validator, or the header contains `*`, the endpoint returns `304 Not Modified`, includes the current `ETag`, and returns no representation body. A non-matching or absent `If-None-Match` returns the existing `200 OK` public projection plus the current `ETag`.

The Listing must still be successfully resolved as `Published` before conditional evaluation. Missing and Draft Listings therefore retain the existing concealed `404 Not Found`, and invalid identifiers retain `400 Bad Request`.

This decision applies only to the direct public Listing-detail route. The paginated public collection from ADR-0039 is unchanged because a page validator would need separate invalidation semantics for collection membership and ordering.

This ADR does not define a positive cache freshness lifetime, CDN policy, `Cache-Control` directive for public responses, Last-Modified timestamps, or conditional behavior for authenticated management endpoints.

No persistence, Domain, or Application schema/contract change is required.

## Consequences

Clients that already know a public Listing identifier can cheaply revalidate an unchanged representation and receive `304 Not Modified` instead of the full JSON body.

The internal Listing version remains absent from public JSON and is not directly observable from the validator. Future public representation revisions can deliberately rotate the validator derivation without changing persisted data.

Public collection caching and any freshness policy remain separate transport decisions.
