# ADR-0036: Owner-only Property replacement with optimistic concurrency

## Status

Accepted and implemented.

## Context

ADR-0034 established immutable internal management ownership for newly created Properties and concealed direct access to missing, non-owned, and legacy-unowned rows. ADR-0035 added the authenticated owner's Property management collection. The remaining management gap is editing an owned Property.

Property is persisted as a full-state record and currently has no lifecycle state that would make only a subset of its fields editable. Its optional values also need unambiguous clearing semantics. Concurrent administrative edits must not silently overwrite each other.

## Decision

Diyarak exposes authenticated owner-only full replacement through:

`PUT /api/market/properties/{propertyId}`

The request contains a required positive `version` plus the same Property detail representation accepted by Property creation. `category` and `address` remain required. Omitted optional values are replacement values and therefore become absent; this is intentionally full replacement rather than PATCH semantics.

`Id` and `OwnerUserId` are immutable and are never accepted from the request.

Property receives a persisted positive numeric `Version`:

- new Properties start at version `1`;
- existing rows are backfilled to version `1` by migration;
- `version` is an EF Core concurrency token;
- a successful replacement increments the persisted version by one;
- an expected version that is already stale returns `409 Conflict` with `market.property.concurrent_modification`.

The owner check is performed using the mapped internal actor identifier. Missing Properties, Properties owned by another user, and legacy rows with no owner all return the same concealed `404`.

Successful replacement returns `200 OK` with the Property identifier and new version. Property creation and management read responses also expose the current version so clients can perform a later conditional replacement.

No ownership transfer, delegation, delete/archive behavior, public Property exposure, or Listing-to-Property ownership coupling is introduced by this decision.

## Persistence migration

The PostgreSQL migration adds nullable `version`, sets existing rows to `1`, then makes the column non-null. It does not modify `owner_user_id` and therefore does not assign ownership to legacy rows.

## Consequences

Property editing now has deterministic replacement and lost-update protection. Optional fields can be cleared without introducing PATCH presence wrappers. Clients must read or retain the current version before replacing a Property.

Future partial editing, ownership transfer, deletion, archival, public search, and authorization relationships between Property ownership and Listing publication remain separate requirements.
