# ADR-0022: Define the Market Listing publication HTTP contract

**Status:** Accepted

## Decision

The Diyarak API contract for publishing an existing Market Listing uses `POST /api/market/listings/{listingId}/publish`.

The operation has no request body and completes synchronously.

The response contract is:

- `204 No Content` when publication and persistence succeed.
- `400 Bad Request` when the Listing identifier is malformed or empty.
- `404 Not Found` when the Listing does not exist or the authenticated caller does not own it.
- `409 Conflict` when the referenced Property does not exist or the Listing cannot transition to `Published` from its current state.
- `500 Internal Server Error` for unexpected infrastructure or programming failures.

Expected failures use RFC Problem Details with a stable application error code in the `code` extension and the request trace identifier in the `traceId` extension.

The stable publication error codes are:

- `market.listing.invalid_id`
- `market.listing.invalid_actor_id`
- `market.listing.not_found`
- `market.listing.property_not_found`
- `market.listing.cannot_publish`

`PublishListingUseCase` returns a `Result` with a classified Application error for expected outcomes. It does not use generic exceptions to communicate expected transport behavior.

Unexpected persistence and infrastructure exceptions are not converted into expected Application failures. They continue to the Host's exception-handling boundary.

ADR-0023 requires an authenticated caller and permits publication only when the caller's user identifier equals the Listing's immutable `PublisherUserId`. A non-owner receives the same `market.listing.not_found` outcome and `404 Not Found` response as a missing Listing so resource existence is not disclosed.

`market.listing.invalid_actor_id` is a defensive Application validation outcome. It does not replace the Host's responsibility to authenticate the caller and supply a non-empty user identifier.

Because the authentication mechanism and claims mapping are not yet defined, the publication route must not be mapped or exposed by `Diyarak.Api`.

Authentication implementation, claims mapping, administrative overrides, ownership transfer, and the final endpoint implementation remain separate decisions.
