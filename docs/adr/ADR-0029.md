# ADR-0029: Edit owned Draft Market Listings with explicit version concurrency

**Status:** Accepted

## Decision

Diyarak will expose authenticated partial editing for an existing Market Listing through `PATCH /api/market/listings/{listingId}`.

Only the internal user identified by the ADR-0025 mapped-user flow and equal to the Listing's immutable `PublisherUserId` may edit the Listing. A missing Listing and a Listing owned by another mapped user both return the same concealed `404 Not Found` result.

Only `Draft` Listings may be edited. An edit attempted after publication returns `409 Conflict` with `market.listing.cannot_edit`.

The update is partial. Omitting a field preserves the current value. `context`, `headline`, and `price` may be replaced with valid values but may not be cleared. `availableFromDate` is optional: omitting it preserves the current value, supplying a valid `yyyy-MM-dd` string replaces it, and explicitly supplying JSON `null` clears it.

The request must include a positive `version`. Every persisted Listing has a positive numeric version starting at `1`; the creation response now includes that initial version so callers do not need to infer it. A successful Listing mutation writes `version + 1`. If the supplied version does not match the loaded Listing version, or if another transaction changes the Listing after it is loaded but before the save commits, the operation returns `409 Conflict` with `market.listing.concurrent_modification`.

The same numeric version replaces ADR-0028's status-only EF Core concurrency token. `MarketListingRecord.Version` becomes the concurrency token used by all current Listing updates, including publication. Publication therefore remains protected from stale competing writes while the same mechanism now also protects Draft editing.

`UpdateListingUseCase` owns the edit orchestration. Required transport parsing occurs in the Host, while ownership, Draft-state, expected-version, domain mutation, transaction, and persistence decisions remain outside the HTTP layer. The persistence-sensitive edit runs through ADR-0027's existing `IMarketTransactionRunner` using the same PostgreSQL `ReadCommitted` transaction boundary.

Successful PATCH requests return `200 OK` with the Listing identifier and the next version so the caller can submit that version with a later edit.

## Transport shape

The editable request properties are:

- `version`: required positive integer;
- `context`: optional object containing string `publishingRole` and `transactionIntent` enum names;
- `headline`: optional non-empty string;
- `price`: optional object. `{ "isOnRequest": true }` represents an on-request price. A known price uses `{ "isOnRequest": false, "amount": <decimal>, "currency": "EUR" }` or another valid three-letter currency code;
- `availableFromDate`: optional `yyyy-MM-dd` string or explicit `null` to clear the value.

A PATCH that contains no editable fields is rejected with `400 Bad Request` and `market.listing.no_changes`. Invalid transport values are rejected with `400 Bad Request` and `market.listing.invalid_patch`.

## Persistence migration

The PostgreSQL migration adds a required `bigint` `version` column to `market.listings`. Existing rows are assigned version `1` before the column is made non-null. No permanent database default is introduced; new rows receive their initial version from the domain aggregate.

## Boundaries

This decision does not define:

- editing a Published Listing;
- Listing ownership transfer or administrative overrides;
- automatic retry or merge of conflicting patches;
- Property row locking or stronger transaction isolation;
- Property lifecycle interactions after Listing creation;
- a general-purpose public Listing read endpoint; or
- edit behavior for future Listing fields not listed above.

Those behaviors require separate requirements.

## Consequences

Draft edits no longer use last-write-wins semantics. Clients receive an explicit version and can detect stale updates deterministically. Publication and Draft editing share one aggregate-level optimistic concurrency mechanism instead of maintaining separate rules for each mutation.
