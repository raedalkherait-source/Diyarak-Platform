# ADR-0032: Load Market Listings directly for the authenticated creator

**Status:** Accepted

## Context

ADR-0026 introduces authenticated Listing creation through `POST /api/market/listings` and returns a `Location` header using `/api/market/listings/{listingId}`. ADR-0029 adds authenticated creator-only Draft editing on that same resource identifier, and ADR-0023 already requires creator-only authorization with concealed `404 Not Found` behavior for non-owners.

The Listing repository can already reconstruct complete current Listing state, but no HTTP `GET` resolves the creation `Location`. Public Listing detail presentation, search, address visibility, contact presentation, and published-listing discovery remain undefined and must not be inferred from the internal management model.

A direct authenticated creator-only read closes the resource-management gap without defining a public publication contract.

## Decision

Diyarak will expose creator-only direct Listing loading through:

`GET /api/market/listings/{listingId}`

The route is mapped only when ADR-0025 authentication is enabled and requires the existing `mapped-user` authorization policy. Missing or invalid access tokens therefore return `401`, and valid but unmapped external identities return `403`.

The route accepts only a non-empty GUID Listing identifier. An invalid identifier returns `400 Bad Request` with stable error code `market.listing.invalid_id`.

`GetListingUseCase` receives the Listing identifier and the mapped internal actor `User.Id`, loads through `IMarketListingRepository.FindByIdAsync`, and applies the established creator-ownership rule. A missing Listing and a Listing owned by another user both return the same `404 Not Found` result with stable error code `market.listing.not_found`.

A successful creator read returns `200 OK` and the current Listing management state: Listing identifier, persisted version, lifecycle status, immutable subject reference, optional context, optional headline, optional price, and optional available-from date. The internal `PublisherUserId` is used for authorization but is not included in the HTTP response.

Both `Draft` and `Published` Listings may be loaded by their creator. This read does not mutate domain state, does not re-check Property existence, and does not require an application transaction boundary.

No database schema or persistence-adapter change is required. The existing Listing repository already performs the required full-state load.

## Consequences

The `Location` returned by Listing creation now resolves to a supported authenticated creator-management resource, and clients can read the current persisted `Version` before issuing a versioned Draft update.

This ADR does not define anonymous/public Listing detail pages, Listing search, public address visibility, contact/publisher presentation, administrative reads, ownership transfer, or additional lifecycle behavior.
