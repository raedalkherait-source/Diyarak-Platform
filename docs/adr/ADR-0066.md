# ADR-0066: Publication time, newest-first search and saved searches

## Status

Accepted.

## Context

Listings had no timestamps. Public search was ordered by listing id, which is effectively random,
so the newest offers were not shown first. Visitors also had no way to come back to a search and
see what is new since their last visit. Alerts by SMS or email need a delivery channel and its
costs, which have not been decided yet.

## Decision

- **Publication time:**
  - `Listing.PublishedAt` is set once, from the application clock, when a draft is published.
  - It is stored in `market.listings.first_published_at`.
  - The check constraint `(status = 1) = (first_published_at IS NULL)` keeps it consistent with
    the status.
  - The migration `MarketListingFirstPublishedAt` backfills existing non-draft listings with the
    migration time.
- **Search order:**
  - Public search is ordered newest first: `first_published_at DESC`, then `id` for stable paging.
  - It is served by the index `(status, first_published_at DESC, id)`.
- **Saved searches** (`market.saved_searches`, migration `MarketSavedSearches`):
  - A user can keep at most 20, each with a name of up to 80 characters.
  - The search is stored as a canonical filter query. The API keeps only the public search's
    filter keys, sorts them, and validates them with the same parser as the public search.
    Equivalent searches therefore compare equal, and a unique index `(user_id, query)` rejects
    duplicates.
  - Each saved search has a `last_seen_at`. Listing a user's saved searches returns, for each
    one, the number of matching listings published after `last_seen_at`. The count is capped at
    99, and the portal shows "+99" above that.
  - API: `GET /api/market/saved-searches`, `POST /api/market/saved-searches` with
    `{ name, query }`, `POST /api/market/saved-searches/{id}/seen`, and
    `DELETE /api/market/saved-searches/{id}`. All are scoped to the signed-in user.
- **Portal:**
  - **Search page:** a "احفظ هذا البحث" button. Signed-out visitors sign in first and return to
    the same search.
  - **`/my/searches`:** shows the "N جديد" badge. Opening a search marks it seen through a POST
    server action, never a GET, so link prefetching cannot reset the count.
- **Cache freshness:** public listing responses in the portal carry the cache tag
  `public-listings`. It is invalidated when a publisher publishes, edits, changes the status or
  photos of a listing, and when a saved search is opened. A user who sees "2 new" then sees those
  listings immediately, not after the 30-second revalidation window.

## Consequences

- Alerts are in-site only for now. An SMS, email or push channel can reuse the same "published
  after" count.
- Listings published before the migration share one timestamp, so their relative order falls back
  to their id.
