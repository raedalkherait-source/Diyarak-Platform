# ADR-0030: Create Market Property assets through authenticated application orchestration

**Status:** Accepted

## Context

ADR-0026 allows an authenticated mapped user to create a `Draft` Listing only when the referenced Property already exists. The Market Property aggregate and complete PostgreSQL persistence representation already exist, but there is no application workflow or HTTP contract that creates a Property asset. As a result, the supported Listing creation flow still depends on pre-existing or manually seeded Property rows.

Property ownership, Property editing, archival/removal, and administrative delegation are not defined by current requirements. Those concerns must not be invented as part of introducing initial Property creation.

## Decision

Diyarak will expose authenticated Market Property creation through:

`POST /api/market/properties`

The route is mapped only when ADR-0025 authentication is enabled and requires the existing `mapped-user` authorization policy. A valid mapped identity is therefore required to create a Property.

The initial create request may supply only Property concepts already supported by the current `Diyarak.Market.Property.Property` aggregate:

- required `category`;
- required address: `street`, `houseNumber`, `postalCode`, and `city`;
- optional geographic `location` containing latitude and longitude;
- optional living, usable, sales, and total areas with value and unit;
- optional total rooms, bedroom count, bathroom count, furnishing quality, features, construction year, last modernization year, commercial subtype, and parking-space count.

Enum values are represented by their current symbolic names. Unknown values or invalid combinations are rejected as validation failures rather than converted into new domain meanings.

The server generates the Property identifier. `CreatePropertyUseCase` constructs the existing Property aggregate and inserts it through a new Application-owned `IMarketPropertyRepository` port. `Diyarak.Platform.Persistence.PostgreSql` implements that port through the existing full-state `MarketPropertyRecord` mapping and `market.properties` table.

Successful creation returns `201 Created`, a body containing the generated `propertyId`, and a `Location` header using `/api/market/properties/{propertyId}`. Invalid request data returns `400 Bad Request` with stable error code `market.property.invalid_create_request`. Missing or invalid access tokens continue to return `401`, and valid but unmapped identities return `403` through ADR-0025.

Authentication authorizes access to the creation capability but does not introduce Property ownership. The mapped internal user identifier is not persisted on the Property because no Property-owner invariant, transfer rule, or authorization model has been accepted. Listing ownership remains independently defined by `PublisherUserId`.

The initial creation operation is a single Property insert and relies on the repository save as its persistence boundary. It does not introduce Property update/delete workflows, ownership, versioning, row locking, or additional transaction semantics.

## Consequences

A caller can now create a Property asset through a supported API and immediately use its identifier with the ADR-0026 Listing creation workflow. The existing Property domain model remains the source of validation for supported fields and combinations, and persistence continues to use the already established full-state record mapping.

Future Property loading, editing, ownership, archival/removal, lifecycle, concurrency, and authorization behavior remain separate decisions.
