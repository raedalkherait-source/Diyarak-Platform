# ADR-0020: Use Integration-owned persistence models for domain aggregates

**Status:** Accepted

## Decision

Entity Framework Core persistence models and mappings belong to Integration projects.

Domain aggregates and value objects remain persistence-ignorant. They must not gain Entity Framework annotations, parameterless constructors, mutable setters, or persistence-only backing members solely to support materialization.

An Integration-owned persistence model may differ structurally from its domain aggregate. Translation between persistence state and domain objects must be explicit at the Integration boundary and must reconstruct objects through their valid domain APIs.

A persisted aggregate record must contain the state required to reconstruct a valid aggregate. An identity-only Property row must not be treated as a persisted Property.

`Diyarak.Platform.Persistence.PostgreSql` may reference Application projects whose ports it implements. It may reference a business Module when an adapter must translate that Module's aggregates, while the Module and Application projects remain independent of the Integration.

The initial PostgreSQL implementation of `IPropertyExistenceChecker` may query the persisted Property identifier without reconstructing the full aggregate, because the existence query does not expose persistence state or domain behavior.

Concrete table and column mappings, repository ports, transaction boundaries, migrations, and Listing persistence remain separate implementation decisions.
