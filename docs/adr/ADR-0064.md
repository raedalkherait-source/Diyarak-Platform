# ADR-0064: Saved listings (favorites)

## Status

Accepted.

## Context

Visitors compare several properties before contacting anyone. Without a way to save listings they
lose track of them, or never come back. Favorites need a signed-in user so they follow the user
across devices. Phone sign-in already exists (ADR-0052).

## Decision

- **Storage:** `market.listing_favorites`.
  - Primary key `(user_id, listing_id)`, so saving twice is harmless.
  - Index `(user_id, created_at DESC)` for the favorites page.
  - No foreign keys, consistent with the other market tables.
- **Rules:**
  - Only a currently published listing can be saved; anything else is a concealed `404`.
  - At most 200 favorites per user (`409 market.favorite.limit_reached`).
  - A saved listing that is later paused, closed or suspended is hidden from the list but kept, so
    it comes back if it is published again.
- **API** (signed-in users):
  - `GET /api/market/favorites?page=&pageSize=` returns the public listing representation, most
    recently saved first, with `Cache-Control: no-store`.
  - `GET /api/market/favorites/{listingId}` returns `{ listingId, isFavorite }`.
  - `PUT /api/market/favorites/{listingId}` returns `204` and is idempotent.
  - `DELETE /api/market/favorites/{listingId}` returns `204` and is idempotent.
- **Portal:**
  - **Listing page:** a client-side save button that talks to the same-origin proxy
    `/api/favorites/{id}`. The listing page itself stays cacheable, and the session token never
    reaches browser JavaScript.
  - **Visitors who are not signed in** get a sign-in link that returns to the listing.
  - **`/my/favorites`:** lists the saved listings. It is protected by the existing middleware.

## Consequences

- Favorites are private: there is no public count per listing, so popularity cannot be scraped.
- Saved searches with alerts are a separate decision, because they need a notification channel.
