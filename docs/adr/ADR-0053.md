# ADR-0053: Listing photos

## Status

Accepted

## Context

A property marketplace is not usable without photos. Phone photos also routinely embed EXIF
metadata, including the GPS coordinates of where they were taken. For a Listing photographed at
the owner's home, publishing that metadata would expose the owner's exact location.

## Decision

Domain (`Diyarak.Market.Listing`):

- `ListingPhoto` is a separate aggregate referencing a Listing: identifier, Listing identifier,
  opaque storage key, format (`Jpeg`, `Png`, `Webp`), size, zero-based position (position `0`
  is the cover) and upload time. At most 30 photos per Listing and 10 MB per photo.

Application (`Diyarak.Market.Application.Photos`):

- `UploadListingPhotoUseCase` reads at most 10 MB and detects the format from the file signature
  (the client `Content-Type` is ignored). It removes metadata without re-encoding pixels:
  - JPEG: drops APP1–APP15 (EXIF, XMP, IPTC, …) except APP14 Adobe, plus comments; keeps
    JFIF, ICC profile and quantisation/Huffman tables; preserves only the EXIF Orientation
    value in a minimal EXIF segment so photos still display upright.
  - PNG: drops `eXIf`, `tEXt`, `zTXt`, `iTXt`, `tIME`.
  - WebP: drops `EXIF` and `XMP ` chunks, clears the VP8X flags and rewrites the RIFF size.
  The sanitized bytes are stored first. If recording the photo then fails because the position
  is taken concurrently, the stored object is deleted.
- Only the Listing creator can add or remove photos, and only while the Listing is a `Draft`,
  consistent with ADR-0029. Missing and non-owned Listings share one concealed not-found result
  (ADR-0023).
- Public Listing projections (detail and collection) include photos in position order. The
  collection loads photos for the whole page in one query.

Ports and adapters:

- `IListingPhotoRepository` → PostgreSQL table `market.listing_photos` (migration
  `MarketListingPhotos`), with unique `(listing_id, position)` and unique `storage_key`.
- `IListingPhotoStorage` → new Integration `Diyarak.Platform.Storage.FileSystem`, writing
  atomically under `Media:FileSystem:RootPath` (default `<content root>/App_Data/media`).
  Keys are generated server-side (`listings/{listingId}/{photoId}.{ext}`) and validated
  against a strict pattern. Paths cannot escape the root.

HTTP:

| Route | Access | Result |
| --- | --- | --- |
| `POST /api/market/listings/{id}/photos` (raw image body) | creator, Draft | `201` + metadata; `413` too large; `415` unsupported; `400` invalid; `409` not Draft / limit / concurrent |
| `GET /api/market/listings/{id}/photos` | creator | ordered metadata |
| `GET /api/market/listings/{id}/photos/{photoId}/content` | creator | image, `no-store` |
| `DELETE /api/market/listings/{id}/photos/{photoId}` | creator, Draft | `204` |
| `GET`/`HEAD /api/market/public/listings/{id}/photos/{photoId}` | anonymous, Published only | image, `Cache-Control: public, max-age=31536000, immutable`, strong `ETag`, `304` on match; `404` + `no-store` otherwise |

Public Listing responses gain `photos: [{ photoId, url }]`.

## Consequences

Listings can carry photos without leaking owners' locations. Photo identifiers are immutable,
so CDNs and browsers can cache public photos indefinitely.

Open work:

- Resized variants and thumbnails, ideally by an image proxy or CDN in front of the public route.
- Reordering photos and editing photos after publication, which needs a decision on post-publication
  Listing changes.
- An S3-compatible storage adapter for multi-node deployments.
- Deleting photo objects when a Listing is removed. Listing removal does not exist yet.
