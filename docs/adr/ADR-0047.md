# ADR-0047: HEAD parity for anonymous public Listing reads

## Status

Accepted

## Context

ADR-0038 and ADR-0039 expose anonymous read-only HTTP resources for published Listing detail and bounded collection pages. ADR-0044 and ADR-0045 add opaque ETag validators, and ADR-0046 defines mandatory revalidation caching for successful public representations. Clients may need to test resource existence or validator freshness without transferring the JSON representation.

Defining separate business behavior for that probe would create unnecessary drift from the existing GET contracts.

## Decision

The two existing anonymous public Listing resources support both `GET` and `HEAD`:

- `/api/market/public/listings/{listingId}`
- `/api/market/public/listings?page={page}&pageSize={pageSize}`

`HEAD` uses the same routing, validation, Application use cases, persistence reads, publication visibility rules, pagination coordinates, ETag generation, `If-None-Match` handling, and cache policy as the corresponding `GET`.

For an existing published representation, `HEAD` returns `200 OK` with the same current `ETag` and `Cache-Control: public, no-cache` headers that the equivalent `GET` would produce, but without a response body. A matching `If-None-Match` validator returns `304 Not Modified`, also without a body.

For direct detail, malformed identifiers return `400` and missing or Draft Listings return the existing concealed `404`. For collection pages, invalid pagination returns `400`. Expected `400` and `404` HEAD responses use the ADR-0046 `Cache-Control: no-store` policy and contain no Problem Details body.

The routes remain anonymous and remain mapped when OIDC management authentication is disabled.

## Consequences

- Clients can probe public Listing resources and revalidate ETags without transferring JSON bodies.
- GET and HEAD cannot diverge in publication visibility or pagination because they share handlers and use cases.
- HEAD still performs the underlying read required to determine current status and validator state.
- No `Content-Length` contract is introduced.
- No positive freshness lifetime, search/filter/ranking behavior, public Property projection, lifecycle transition, or authorization rule is introduced.
- No schema or migration change is required.
