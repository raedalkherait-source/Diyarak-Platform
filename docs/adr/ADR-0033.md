# ADR-0033: List Market Listings owned by the authenticated creator

**Status:** Accepted

## Context

ADR-0026 creates Listings owned by the mapped internal actor, ADR-0032 allows that creator to load one known Listing directly, and ADR-0029 allows creator-only Draft editing. A mapped user can therefore manage a Listing when its identifier is already known, but there is no management collection endpoint that lets the user recover the Listings they own.

Public Listing discovery, search, ranking, pagination, public detail presentation, and administrative Listing access remain undefined. Those concerns must not be inferred from the authenticated creator-management model.

A creator-scoped collection closes the management gap without defining public search or new ownership semantics.

## Decision

Diyarak will expose the authenticated creator's Listing collection through:

`GET /api/market/listings`

The route is mapped only when ADR-0025 authentication is enabled and requires the existing `mapped-user` authorization policy. Missing or invalid access tokens return `401`, and valid but unmapped external identities return `403`.

`ListOwnedListingsUseCase` receives only the mapped internal actor `User.Id`. It does not accept a publisher identifier from request data. The Application-owned `IMarketListingRepository` adds `FindByPublisherUserIdAsync`, and the PostgreSQL adapter performs a no-tracking query constrained by `PublisherUserId` before reconstructing domain Listings.

A successful request returns `200 OK` with an array of the same authenticated management representation used by ADR-0032: Listing identifier, persisted version, lifecycle status, immutable subject reference, optional context, optional headline, optional price, and optional available-from date. `PublisherUserId` is used for filtering and authorization but is not emitted in the response.

When the authenticated creator owns no Listings, the endpoint returns `200 OK` with an empty array. Listings owned by another user are not included.

This initial creator-management collection has no filtering, search, pagination, or ordering contract. The persistence query does not promise result order. Those capabilities require separate concrete requirements before implementation.

No database schema change, application transaction, Property existence re-check, or Listing lifecycle mutation is introduced.

## Consequences

Authenticated users can now recover their own Listing management resources without already knowing each Listing identifier, while the established immutable `PublisherUserId` remains the sole ownership key.

The endpoint is not a public Listing search or discovery API. It does not define anonymous access, public address/contact presentation, administrative reads, sorting, pagination, filtering, ranking, or cross-owner visibility.
