# ADR-0021: Load and save Listings within publication orchestration

**Status:** Accepted

## Decision

`PublishListingUseCase` will receive a Listing `Guid` identifier rather than a preloaded Listing aggregate.

The Application layer will own an `IMarketListingRepository` port that loads an existing Market Listing and saves its resulting state.

The publication workflow is:

1. Load the Listing by identifier.
2. Reject the operation when the Listing does not exist.
3. Verify through `IPropertyExistenceChecker` that the referenced Property exists.
4. Invoke the Listing aggregate's `Publish()` behavior.
5. Save the resulting Listing state.

The repository save operation is the current persistence commit boundary. Concrete persistence records, mappings, queries, and EF Core concerns remain in Integrations according to ADR-0020.

When PostgreSQL composition is used, the Listing repository and Property existence checker are scoped services backed by the same `PlatformDbContext`.

No explicit transaction, lock, or isolation guarantee spans the Property existence query and Listing save until Property removal or lifecycle concurrency behavior is defined.

Hosts provide input identifiers and invoke the Application use case; they do not load aggregates, perform publication checks, or save domain state themselves.

Transport contracts, API error mapping, optimistic concurrency, Listing creation persistence, and behavior when a Property becomes unavailable after publication remain separate decisions.
