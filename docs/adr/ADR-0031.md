# ADR-0031: Load Market Property assets by identifier through authenticated application orchestration

**Status:** Accepted

## Context

ADR-0030 introduces authenticated Property creation through `POST /api/market/properties` and returns a `Location` header using `/api/market/properties/{propertyId}`. The Property aggregate and PostgreSQL full-state mapping already support reconstructing the complete asset, but no Application or HTTP read workflow currently resolves that location.

The Market requirements also allow an existing Property to be reused when creating another Listing. A direct by-identifier read is useful for that authenticated asset workflow, while search, public presentation, Property ownership, editing, removal, and address-visibility rules remain undefined.

Publishing a full Property asset anonymously would prematurely decide public address visibility. The requirements explicitly keep public address display as a Listing concern, so the initial Property read must not become a public listing-detail contract.

## Decision

Diyarak will expose authenticated direct Property loading through:

`GET /api/market/properties/{propertyId}`

The route is mapped only when ADR-0025 authentication is enabled and requires the existing `mapped-user` authorization policy. Missing or invalid access tokens therefore return `401`, and valid but unmapped external identities return `403`.

The route accepts only a non-empty GUID Property identifier. An invalid identifier returns `400 Bad Request` with stable error code `market.property.invalid_id`. A valid identifier that does not resolve to a persisted Property returns `404 Not Found` with stable error code `market.property.not_found`.

`GetPropertyUseCase` owns the Application orchestration and loads through `IMarketPropertyRepository.FindByIdAsync`. The PostgreSQL adapter performs a no-tracking lookup and reconstructs the existing Property aggregate through the established full-state mapper.

A successful read returns `200 OK` and the currently modeled Property state: identifier, category, address, optional geographic location, optional living/usable/sales/total areas, optional room counts, optional furnishing quality, features, building years, optional commercial subtype, and parking-space count. Enum values and area units use their current symbolic names.

The authenticated read does not create Property ownership or per-user authorization. Any mapped user with a known Property identifier may load the asset. This is an authenticated asset-management contract, not a public Listing presentation contract; it does not decide whether street or house-number information is displayed on public listings.

No database schema change is required. The current `market.properties` table and full-state mapping already contain the data needed for the read.

## Consequences

The `Location` returned by ADR-0030 now resolves to a supported authenticated resource, and a mapped caller can load a known Property before reusing its identifier for Listing creation.

Property search/list endpoints, public Property presentation, editing, removal/archive behavior, ownership, lifecycle, concurrency, and additional authorization remain separate decisions.
