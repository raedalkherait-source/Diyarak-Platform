# ADR-0028: Detect competing Market Listing publication with optimistic status concurrency

**Status:** Accepted

## Decision

Market Listing publication will use optimistic concurrency on the persisted Listing status so two transactions that both loaded the same `Draft` Listing cannot both successfully persist publication.

`IMarketListingRepository` replaces the unconditional publication save with `TrySaveAsync(Listing listing, ListingStatus expectedStatus, ...)`. `PublishListingUseCase` always supplies `ListingStatus.Draft` as the expected persisted status after the domain aggregate has successfully transitioned to `Published`.

The PostgreSQL adapter configures `MarketListingRecord.Status` as an EF Core concurrency token. When saving a publication, the adapter attaches the translated record, supplies `Draft` as the original status, and attempts `SaveChangesAsync`. EF Core therefore includes the expected status in the update concurrency predicate.

If no row matches because another committed write already changed the status, EF Core raises `DbUpdateConcurrencyException`. The repository converts that expected persistence race into `false` rather than leaking an EF Core exception across the Application port. `PublishListingUseCase` then returns the stable conflict error `market.listing.concurrent_modification`, and the existing Host error mapping returns `409 Conflict`.

The first competing transaction that successfully changes the persisted state from `Draft` wins. A stale transaction that had already loaded the old `Draft` state receives the concurrency conflict. A later request that starts after publication has committed loads the already-published aggregate and continues to receive the existing `market.listing.cannot_publish` conflict.

The transaction boundary from ADR-0027 remains `ReadCommitted`; this decision does not introduce pessimistic row locking or stronger isolation.

The EF Core model snapshot is advanced with a metadata-only migration. The migration has no PostgreSQL DDL because the existing `status` column is sufficient; only EF Core concurrency metadata changes.

## Boundaries

This decision protects the currently defined `Draft` to `Published` transition against stale competing publication writes. It does not define general aggregate versioning for future draft-edit operations.

This decision does **not** introduce:

- a numeric or timestamp Listing version exposed by the domain or HTTP API;
- `ETag`, `If-Match`, or another client-supplied concurrency token;
- automatic retry of a failed publication;
- pessimistic row locks;
- `RepeatableRead` or `Serializable` isolation;
- optimistic concurrency rules for future draft editing or other Listing mutations; or
- Property mutation/removal concurrency rules.

Those behaviors remain separate requirements and must be defined when the corresponding operations exist.

## Consequences

Competing publication attempts no longer rely on last-write-wins behavior. The Application layer receives a persistence-neutral success/failure signal for the expected status check, while EF Core-specific concurrency handling remains inside the PostgreSQL integration.

The HTTP publication contract gains one additional stable `409 Conflict` code, `market.listing.concurrent_modification`, without changing the route or authentication and ownership rules defined by ADR-0022, ADR-0023, and ADR-0025.
