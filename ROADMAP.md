# Engineering Roadmap

1. **Foundation 1.0** — repository, primitives, shared kernel, building blocks, contracts.
   - Status: baseline complete.

2. **Platform Core 0.5** — identity, authorization, reference data, audit, media, relationship, listing, search, notification.
   - Status: structure complete. Identity has an implemented domain baseline, and Platform Listing has an initial sector-agnostic subject-reference baseline; remaining capabilities are foundation scaffolds pending concrete requirements.

3. **Diyarak Market 1.0** — property, company, and listing modules, public/admin APIs, and search.
   - Status: in progress. Property has an initial domain baseline covering aggregate identity, optional persisted management ownership for legacy-safe rehydration, supported top-level categories, required property address, optional geographic location, optional living, usable, sales, and total areas, optional room counts, optional furnishing quality, optional property features, optional building years, optional parking-space count, and optional commercial-property subtype; Company remains a foundation scaffold. Market Listing has an initial aggregate baseline with Listing identity, a required immutable non-empty `PublisherUserId`, a required immutable sector-agnostic subject reference that currently accepts only `market.property`, `ListingContext`, `ListingPrice`, `ListingHeadline`, and optional `ListingAvailableFromDate`. The initial Listing lifecycle supports creation as `Draft` and an explicit transition to `Published`; publication requires context, headline, and price, and core publication data can be edited only while the Listing is `Draft`. `Diyarak.Market.Application` owns the `IMarketListingRepository` and `IPropertyExistenceChecker` ports. `PublishListingUseCase` receives Listing and authenticated actor user identifiers, validates creator ownership before the Property query, conceals missing and non-owned Listings with the same not-found result, invokes `Listing.Publish()`, saves the resulting state, and returns classified validation, not-found, or conflict errors for expected failures. `Diyarak.Platform.Persistence.PostgreSql` provides full-state Property and Listing records including legacy-safe Property management ownership and Listing publisher ownership, explicit domain mappings, the `market.properties` and `market.listings` migrations, the safe no-default Listing ownership migration, the Property existence checker, and the Market Listing repository. ADR-0022 and ADR-0023 define the publication HTTP contract and creator-only authorization, including concealed `404` responses for non-owned Listings. ADR-0024 defines the safe ownership migration strategy. ADR-0025 is implemented in `Diyarak.Api` and `Diyarak.Platform.Persistence.PostgreSql`: the Host validates explicitly configured JWT bearer access tokens, resolves exact external `(iss, sub)` identities through persistent mappings to internal `User.Id` values, returns `401` for missing or invalid access tokens and `403` for valid but unmapped identities, and conditionally exposes authenticated Market Listing routes only when authentication is enabled. The publication endpoint passes only the mapped internal actor identifier to `PublishListingUseCase` and preserves the concealed `404` required for mapped non-owners. ADR-0026 defines and implements authenticated `Draft` Listing creation for an existing Property through `POST /api/market/listings`; the mapped internal actor becomes the immutable `PublisherUserId`, Property existence is checked before creation, and the new aggregate is inserted through `IMarketListingRepository.AddAsync`. ADR-0027 defines and implements an explicit Application-owned transaction boundary for Listing creation and publication; the PostgreSQL adapter runs the persistence-sensitive workflow in one `ReadCommitted` transaction and commits only successful Results. ADR-0028 adds optimistic persisted-status concurrency for competing publication attempts. ADR-0029 replaces that status-only token with an explicit numeric Listing version shared by publication and authenticated owner-only Draft editing through `PATCH /api/market/listings/{listingId}`; partial updates preserve omitted fields, `availableFromDate: null` clears the optional date, stale versions return a stable `409`, and successful edits return the next version. ADR-0030 defines and implements authenticated Property asset creation through `POST /api/market/properties`, using only concepts already supported by the then-current Property aggregate and PostgreSQL mapping. ADR-0031 resolves the Property creation `Location` with authenticated `GET /api/market/properties/{propertyId}`. ADR-0032 resolves the Listing creation `Location` with creator-only `GET /api/market/listings/{listingId}` backed by the existing full-state Listing repository; non-owners receive the same concealed `404` as missing Listings, and the response remains an authenticated management representation rather than a public Listing-detail contract. ADR-0033 adds mapped-user-only `GET /api/market/listings` for the current creator's own management collection, filtered by persisted `PublisherUserId` and returning the same management representation without defining public search, pagination, or ordering. ADR-0034 establishes internal Property management ownership: new Properties persist the mapped actor as immutable `OwnerUserId`, direct loading is owner-only with concealed `404` for missing, non-owned, and legacy-unowned rows, and the nullable ownership migration intentionally performs no historical backfill. Identity-provider vendor selection and external-identity provisioning transport, authoritative ownership assignment for legacy Property rows, Property ownership transfer/delegation, Property update/removal workflows, additional Listing operations beyond creator direct loading, creator collection loading, and Draft editing, administrative overrides and ownership transfer, authoritative migration of any legacy Listing ownership, Property row locking or stronger isolation guarantees, additional publication-readiness requirements, lifecycle states and transitions, search, and additional Market behavior remain pending concrete requirements.

4. **Sector Expansion** — services, materials, equipment, opportunities.
   - Status: not started.

5. **Projects and Property Management** — projects, units, management workflows.
   - Status: not started.
